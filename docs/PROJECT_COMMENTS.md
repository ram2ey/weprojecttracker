# Project and news comments

Visitors can post a name (1–80 characters) and plain-text message (1–2,000 characters) on a published project or news story without an account. Comments appear immediately, newest first, in pages of 20. Names are unverified. There are no replies, uploads, automatic links, notifications or email dependencies. Removal requests use the existing office contact options. Sample stories remain read-only.

The `project_comment` table is separate from retired guest submissions, which remain inaccessible. Migration `0010_tearful_lake` adds a nullable news-story reference and makes the project reference nullable; a database constraint requires exactly one subject. Existing project comments are preserved. News has separate commenting and engagement-version fields so editing a story cannot overwrite its moderation settings. A repeated submission identifier from the same browser returns the previous result; a changed payload or subject using that identifier is rejected. Hidden comments remain private and recoverable with no automatic expiry.

Public endpoints:

- GET `/api/public/content/[slug]/comments?page=1`: currently visible comments and the project's commenting state. No guest identifier is returned or set.
- POST `/api/public/content/[slug]/comments/session`: same-origin form activation. Sets `wassa_comment_guard` only when needed: signed, HttpOnly, SameSite=Strict, Secure over HTTPS, 24-hour expiry.
- POST `/api/public/content/[slug]/comments`: strict bounded JSON `{submissionId, displayName, body, website}`. `website` is the empty honeypot. Requires the signed cookie and same origin, but no optional statistics permission.

News uses the same three operations under `/api/public/news/[id]/comments`. Both routes share validation, guards, site-wide/browser posting limits, retry handling and moderation. The UI opens immediately and focuses the message before the name; the guard is prepared on submission. Project-card shortcuts use `#write-comment` when open and the existing-comments heading when closed. The publication state is checked again server-side regardless of the card's state.

Posting limits allow three attempts per browser per ten minutes and 60 site-wide per minute across projects and news; exact successful retries do not spend another attempt. Only HMAC keys enter rate-limit storage. No comment IP addresses are recorded. Expired counters are pruned during submissions. Basic limits do not eliminate spam or impersonation. Publication and posting are checked under the project or story's row lock, so closing and withdrawal serialize with submissions. Closed discussions retain visible comments; withdrawn or unpublished subjects return 404.

Only verified, active operators can access `/admin?view=comments` and GET/PATCH `/api/staff/comments`. The screen filters by project or news story and visible/hidden state. News selector IDs use `news:<uuid>` to distinguish subjects; project IDs keep their existing format. Operators can hide/restore comments and close/reopen either discussion. Withdrawn stories with comments remain available to moderators. Version checks reject stale moderation actions. Audit records contain action/actor/subject IDs, never comment names or messages. Hiding is reversible and is not deletion. No retired guest APIs, worker or public accounts are reactivated.

Tests cover plain-text rendering, failed-response retries, pagination failures, role restrictions, reversible moderation, version conflicts, rate limits, forged cookies, origin and request bounds, retired-data isolation, closure/withdrawal races, analytics denial, accessibility and phone layouts. Migration rehearsal preserves legacy credentials, projects, media and retired comments while creating an empty new table. The protected release pipeline performs the production build, container validation and exact-release live smoke checks. Do not publish fixture projects on production for verification.
