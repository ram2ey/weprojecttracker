# App audit — 5 November 2026

## Assessment

The app has a sound functional foundation and consistent visual styling. Its principal publishing, authentication, moderation, export and offline workflows pass the existing automated checks. The highest priorities are preventing staff work from being lost and giving operators a usable way to revoke staff access. Several less common failure and growth scenarios remain incomplete.

This review records **two high-priority issues, five medium-priority functional issues, two design improvements, and one performance risk**. No critical vulnerability was confirmed. Passing tests and a clean dependency audit do not establish that the app is free of vulnerabilities.

Application source was not changed. Existing changes to the homepage, global styles and design-system document were included in the review and preserved.

## High-priority issues

### A01 — Unsaved staff edits can be lost without warning

**Priority:** P1. **Evidence:** Source-confirmed.

The editor keeps draft text, financials and attachment selections in React state. Revision switching navigates immediately; the register link, sidebar and reload recovery also permit leaving the editor. There is no dirty-state guard, navigation warning or recovery copy. A save conflict explicitly offers a full reload, which discards the current unsaved values.

**Trigger:** Change a long draft, then choose another revision or follow a workspace link before saving. For a conflict, have another officer save the same revision and use “Reload this record” after the rejected save.

**Impact:** Staff can lose substantial work, particularly on long forms or intermittent connections. The server correctly rejects conflicting writes, but the UI does not help recover the rejected work.

**Recommendation:** Track unsaved changes; warn on route/revision changes and browser unload; offer a way to preserve or copy edits before reloading a conflict. Any persistent recovery storage must account for staff-only financial data.

**Locations:** `src/components/content/record-editor.tsx:46`, `:270`, `:1290`.

### A02 — Operators cannot revoke staff access through the app

**Priority:** P1 operational gap. **Evidence:** Source-confirmed across staff UI/API routes.

The staff screen only generates setup/password-recovery links. There is no staff directory, deactivate action, role-change action or operator session-revocation action. Runtime identity checks already honor `staff.active`, but there is no application workflow to change it. Password recovery preserves the existing role and MFA.

**Trigger:** An officer leaves, loses a device, or should no longer have access to private records and financial information.

**Impact:** An operator needs direct maintenance/database intervention to terminate access. Existing session checks support revocation once the underlying account state changes; this is a missing operational control, not a demonstrated authentication bypass.

**Recommendation:** Add an operator-only staff directory with audited deactivation and session revocation, protections against removing the last operator, and a clear account-status display.

**Locations:** `src/components/staff/team-form.tsx:41`; `src/app/api/staff/links/route.ts:28`; `src/lib/security/staff-session.ts:18`.

## Medium-priority functional issues

### A03 — Inbox notices beyond the newest 100 are unreachable

**Priority:** P2. **Evidence:** Source-confirmed.

The inbox endpoint always returns the newest 100 notices, including read notices, while the unread count includes every notice. Neither the endpoint nor UI provides pagination. Marking displayed notices read does not bring older ones into view.

**Trigger:** Accumulate 101 notices with an unread notice outside the newest 100.

**Impact:** The inbox can retain an unread count that users cannot clear or investigate through the inbox.

**Recommendation:** Add cursor pagination and unread filtering; verify that marking the first page read still permits reaching older notices.

**Locations:** `src/app/api/staff/inbox/route.ts:7`, `:11`; `src/components/engagement/staff-inbox.tsx:52`.

### A04 — Public search does not match the project codes displayed by the app

**Priority:** P2. **Evidence:** Source-confirmed SQL mismatch.

Public search includes the raw numeric record number, title, description, community and tags. It never constructs the displayed code, such as `WE-P00123`. Searching that complete code therefore fails unless it happens to appear in another searchable field. Internal report search does construct the full code, producing inconsistent behavior.

**Recommendation:** Search the canonical formatted code, with consistent case handling, alongside the current fields. Verify a published project can be found by copying its displayed code into search.

**Locations:** `src/lib/content/public.ts:84`; compare `src/lib/reports/data.ts:83`.

### A05 — Comment pagination failures are not handled

**Priority:** P2. **Evidence:** Source-confirmed promise/error path.

“More comments” and “Previous comments” call the asynchronous `load()` function directly. That function can reject, and the click handlers do not catch the rejection or set an error/loading state. Initial loading and submission handle errors, but these pagination actions do not.

**Trigger:** Disconnect or receive a non-success response while requesting another comment page.

**Impact:** The old comments remain without an explanation; the request rejects without actionable UI feedback. Repeated clicks can also issue overlapping requests.

**Recommendation:** Handle pagination failures, retain the existing page, show a retry message and prevent overlapping page requests.

**Locations:** `src/components/engagement/guest-discussion.tsx:36`, `:289`, `:294`.

### A06 — Large reports can prevent the report screen from rendering

**Priority:** P2, conditional on data volume. **Evidence:** Source-confirmed control flow; not seeded with 5,001 records during this audit.

`reportData()` throws once more than 5,000 projects match. The screen invokes it before rendering the filter form. The page only handles schema-invalid filters, not this data-limit exception, and the staff routes have no custom error boundary.

**Trigger:** Open `/admin?view=reports` when 5,001 or more projects match the default selection.

**Impact:** The screen fails before presenting the filters needed to narrow the selection. The export safeguard is reasonable, but it also blocks ordinary report browsing.

**Recommendation:** Separate paginated browsing/counts from export limits. Keep filters visible and present an inline “narrow the report” message for oversized exports. Add a staff error boundary with recovery navigation.

**Locations:** `src/lib/reports/data.ts:124`; `src/components/reports/reports-panel.tsx:14`; `src/app/admin/page.tsx:79`.

### A07 — Refreshing an expired guest check clears the composed message

**Priority:** P2. **Evidence:** Source-confirmed client/server behavior.

Guest checks expire after ten minutes. Submission then instructs the visitor to open a new form. The form-opening function unconditionally clears the message body, and there is no separate refresh-check control.

**Trigger:** Spend more than ten minutes composing feedback, submit, then reopen the form as instructed.

**Impact:** The visitor must manually copy their message first or retype it. The server timeout is appropriate; its recovery flow causes avoidable work loss.

**Recommendation:** Refresh the challenge independently of the message fields and preserve the current message on expiration and retry.

**Locations:** `src/lib/engagement/guest.ts:64`; `src/lib/engagement/service.ts:97`; `src/components/engagement/guest-discussion.tsx:64`.

## Design and usability improvements

### A08 — The desktop directory gives filters more prominence than projects

**Priority:** P2 design improvement. **Evidence:** Manual browser observation plus layout source.

At the browser's approximately 1,000px-wide desktop view, the introduction, spacing and fully expanded filter panel occupy essentially the first screen. The result count appears near the bottom and the first project card starts below it. Removing the development-only notice would save some height, but the multirow panel remains the dominant element.

**Recommendation:** Keep search and the most-used filters visible; place date range, subcategory and other advanced filters in an expandable area. Reduce the directory heading's vertical spacing. Aim to show a meaningful part of the first results without scrolling at common laptop sizes.

**Locations:** `src/app/(public)/projects/page.tsx:99`; `src/app/globals.css:2956`, `:1074`.

### A09 — Phone results do not explain most active filters

**Priority:** P2 design improvement. **Evidence:** Source-confirmed and phone layout inspected.

On phones the search and every filter live inside the “Filter projects” sheet. After dismissal, the main results summary only mentions category. It does not expose the keyword, community, status, dates or sort selection, and there are no removable active-filter chips or an applied-filter count.

**Impact:** Visitors can see unexpectedly few or no projects without seeing which choices caused the result. Editing a keyword requires reopening the full filter sheet.

**Recommendation:** Show compact active-filter chips with removal controls and an obvious clear action outside the sheet. Keep keyword search directly accessible on the directory and display an applied-filter count on the trigger.

**Locations:** `src/app/(public)/projects/page.tsx:99`, `:211`; `src/components/ui/responsive-panel.tsx:129`.

## Performance risk requiring measurement

### A10 — Cache hits still require hashing the entire publication register

**Priority:** P2 scalability risk. **Evidence:** Source-confirmed algorithm; production latency impact is unmeasured.

For eligible production HTML requests, `publicRenderVersion()` constructs ordered JSON aggregates over all content records, taxonomy and media, then hashes them. This runs before cache lookup; cache misses perform another version check after rendering. Work therefore grows with the entire register even for a frequently requested cached homepage. Draft records and non-public media also contribute to the version.

**Recommendation:** Benchmark with realistic record/media counts and concurrency. Consider a transactional publication-version row updated by relevant mutations, preserving immediate withdrawal invalidation while making version reads constant-sized. Keep the post-render race check.

**Locations:** `src/lib/content/render-cache.ts:15`; `src/proxy.ts:20`, `:33`.

## What is working well

- The public site uses explicit projections and approved revisions. Tests cover private financial fields, financial files, pending revisions, withdrawals and generated public reports.
- Publishing has independent review, contributor exclusion, immutable submissions and optimistic concurrency checks.
- MFA is enforced after password and provider sessions; replay, recovery-code reuse, deactivation and expired-proof scenarios are tested.
- The visual system has consistent green actions, neutral surfaces, shared controls and readable hierarchy. Illustrations are identified rather than presented as documentary evidence.
- Phone navigation, filter sheets, focus return, reduced-motion behavior and both appearances have automated coverage. No violations were reported by the configured axe scans on the tested states.
- Offline reading is opt-in, bounded and labeled with saved-time/staleness information; staff routes remain excluded from public offline caching.
- Missing map configuration leaves a usable project list, and projects without coordinates remain discoverable.

## Recommended order

1. Prevent unsaved staff work from being lost and implement operator deactivation/session revocation.
2. Fix inbox pagination, code search and comment-pagination error handling.
3. Preserve guest messages when refreshing checks; make report-limit failures recoverable.
4. Simplify the desktop filter panel and expose applied phone filters.
5. Measure the cache-version query at realistic scale, then optimize based on those results.

Additional product polish: the real “Overview” currently renders the same register as “Projects”; either give it useful review/overdue summaries or merge those destinations. The main register also lacks a keyword-search control, making older records increasingly cumbersome to locate as it grows. These are follow-on usability recommendations rather than extra counted findings.
